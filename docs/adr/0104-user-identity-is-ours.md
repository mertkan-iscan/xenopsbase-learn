# ADR-0104: User identity is ours, and `sub` is only a link

- **Status:** Accepted
- **Date:** 2026-08-28
- **Task:** T-0.4 (#4)

## Context

The stemcell's ADR-0010 established two things and confessed a third. It established that the
Keycloak `sub` had quietly become an ownership key, and that its stability was therefore a
data-integrity property rather than an identity detail. It confessed that its fix — pinning
declared users' ids in the realm file — covers only declared users: *"runtime-created users are
out of scope, knowingly"*, and it named the durable fix it was not building: *"a local user
record keyed to `sub` on first sight, so that identity has one level of indirection and a
re-keying becomes a migration instead of data loss."*

This platform creates **every** user at runtime. It inherits exactly the gap ADR-0010 flagged,
multiplied by every customer it ever signs (ADR-0102 works through that multiplication). And it
adds a second force the stemcell never had: per-company SSO (T-1.8). A customer switching
identity providers regenerates `sub` for all of their users through a supported, entirely
unexceptional operation — not an accident to be prevented, a feature to be survived.

## Decision criteria

- What an accidental realm delete costs afterwards, measured in queries rather than in hope
- Whether identity survives a change of identity provider, which per-company SSO makes routine
- How much of the codebase has to know about the difference

## Decision

**`app_user.id` — our own UUID, generated by `identity`, never by Keycloak — is the identity of
a person everywhere in this platform. The Keycloak `sub` is stored once, as `app_user.idp_sub`:
nullable, unique, and repairable.**

The rule for every other table, in every service, stated so it can be enforced:

> A reference to a person is a reference to `app_user.id`. No domain table, in any module,
> stores a `sub` — not as a foreign key, not as an audit column, not as a convenience copy.

Enforced twice rather than reviewed: an ArchUnit rule fails the build on an entity field shaped
like a subject reference outside `identity`'s user package, and a schema test walks
`information_schema` and fails on any column named like one that `app_user` does not own. The
rule is inherited by every service generated from the template (T-9.10), which is what makes
"in every service" a property rather than a hope.

**First-login provisioning.** The row is created idempotently on first sight of a verified
token: look up by `idp_sub`, insert if absent, and let the unique constraint arbitrate the race
when the same person's first two requests arrive concurrently — the loser re-reads. No
provisioning step, no runbook, no admin action.

**The repair.** When a `sub` changes — IdP migration, realm rebuilt, account recreated — the fix
is one UPDATE matched on the verified email inside the tenant, written as a runbook step in
`docs/runbooks/identity.md`. Every foreign key in every service keeps pointing at the same
`app_user.id`; nothing else moves. That one column is the entire blast radius, and that is the
measurement the first decision criterion asks for: a realm delete costs one UPDATE per user,
against the alternative — an archaeology dig across every table of every service for every value
of a key that no longer exists.

**What happens between the break and the repair** is a failed login, loudly: a token whose `sub`
matches no row and whose email matches an existing row provisions nothing and reports the
conflict. Silently auto-relinking on email match would make email ownership equivalent to
account takeover, so re-linking stays a deliberate act.

**Audit columns follow the same rule.** They record `app_user.id`, never a username and never a
`sub` — usernames are mutable (an audit trail a profile edit can rewrite is not an audit trail)
and `sub` is exactly the key this ADR demotes.

## Consequences

### What this makes easy

IdP changes, realm rebuilds and per-company SSO migrations become identity-layer events invisible
to every other service. Cross-service references are uniform — a UUID with one meaning. Display
details live in one place and are resolved through `identity`'s published interface instead of
being copied into tables that would never keep them current.

### What this makes hard

Every request that needs the current user pays the `sub → app_user` resolution, which will want
the same cache discipline as permissions (T-2.5) rather than a lookup per request. `identity`
becomes a dependency of anything that renders a person, which is real coupling — through the
published interface, but coupling.

### What it commits us to

`app_user` is durable state of the first order: losing it now loses the only mapping from people
to everything they did. It sits in `identity`'s Postgres under the same backup discipline as
everything else (the stemcell's ADR-0007/ADR-0008 lineage), and T-1.7's test — realm changes must
not destroy the people in the realm — is the standing proof the indirection keeps working.

## Alternatives considered

### Keep `sub` as the key and forbid the procedures that regenerate it — rejected

This is ADR-0010's world, and ADR-0010 itself documents why it does not extend here: the
forbidden procedures include one this product sells (per-company SSO migration). A rule that
says "never change identity provider" is a product limitation dressed as an architecture
decision, and the first customer contract that requires an IdP change breaks it.

### Mirror runtime users into git with pinned ids — rejected

Scales the stemcell's declared-user fix to a place it was never meant to go: git commits per
sign-up, PII in the repository, and a realm file that races the product for ownership of the
user set. The stemcell pins five dev accounts; a product cannot pin a customer base.

## ADR-0010, and what this changes there

Nothing — verified rather than assumed. ADR-0010's analysis is correct for what the stemcell
ships, it already names this ADR's design as its known successor, and the stemcell's
`docs/runbooks/authorization.md` already scopes the delete-and-reimport procedure to dev in so
many words (*"Never do this in an environment with real users"*). No amendment issue is needed.
This ADR is the successor being built where it is load-bearing, as ADR-0102 recorded.

## Revisit if

- The `sub → app_user` resolution shows up in a latency measurement even with T-2.5's cache in
  place — the indirection's runtime cost would then be a measured fact rather than a design fear.
- A customer's compliance regime requires identity claims to be verifiable end-to-end from the
  IdP without a local mapping in the path — that is a different trust model, and it would need
  its own ADR rather than an exception here.
